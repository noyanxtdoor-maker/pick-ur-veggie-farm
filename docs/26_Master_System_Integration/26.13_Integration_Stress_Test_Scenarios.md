# Integration Stress Test Scenarios

## Purpose

A great ERP system is not measured by how well it performs when everything works perfectly.

It is measured by how safely it behaves when:

- Internet fails
- Devices are lost
- Users make mistakes
- Data conflicts occur
- AI services are unavailable
- Hardware fails
- Human fraud is attempted

This document defines the extreme situations that PickUrVeggie ERP V3 must survive.

---

# Scenario 1: Internet Failure During Farm Operations

Situation:

A worker is recording a harvest in a greenhouse with no internet connection.

Expected System Behavior:

- Worker continues the operation normally.
- Data is saved locally.
- A synchronization queue is created.
- The worker is notified that the record is pending upload.
- Data automatically synchronizes when internet returns.

---

# Scenario 2: Two Workers Record the Same Event

Situation:

Two workers accidentally record the same harvest.

Expected System Behavior:

The system:

- Does not delete either record.
- Detects possible duplication.
- Flags the conflict.
- Sends it for supervisor review.
- Creates an audit trail.

---

# Scenario 3: Employee Attempts Attendance Fraud

Situation:

A worker changes the phone clock to fake a time-in.

Expected System Behavior:

The system records:

- Device time
- Server synchronization time
- Time difference

The attendance record may be flagged for review.

---

# Scenario 4: Lost Employee Phone

Situation:

A worker loses a personal phone containing offline ERP data.

Expected System Behavior:

The administrator:

- Revokes device trust.
- Blocks future synchronization.
- Terminates active sessions.
- Records the security event.

---

# Scenario 5: Unauthorized Financial Access

Situation:

A worker attempts to open financial reports.

Expected System Behavior:

- Access is denied.
- Permission violation is logged.
- Sensitive data remains protected.

---

# Scenario 6: Inventory Error

Situation:

A worker records using 100 kg of fertilizer but only 20 kg exists.

Expected System Behavior:

Normal users:

- Transaction is blocked.

Authorized users:

- May override with:
  - Reason
  - Approval
  - Audit record

---

# Scenario 7: AI Gives Incorrect Recommendation

Situation:

Codex recommends a wrong treatment because the available information is incomplete.

Expected System Behavior:

- Codex identifies whether information comes from ERP data or general knowledge.
- Recommendations are advisory only.
- Human users make final decisions.
- The recommendation history remains available for review.

---

# Scenario 8: IoT Sensor Failure

Situation:

An EC sensor starts giving unrealistic readings because it requires calibration.

Expected System Behavior:

The system:

- Flags abnormal values.
- Shows sensor health warnings.
- Records calibration status.
- Avoids treating unreliable data as trusted information.

---

# Scenario 9: Employee Leaves the Company

Situation:

A former employee still has the application installed.

Expected System Behavior:

- User account is disabled.
- Device trust is revoked.
- Access tokens expire.
- Company information is inaccessible.
- Historical records remain preserved.

---

# Scenario 10: Payment Dispute

Situation:

A customer claims that payment was sent through GCash but no confirmation exists.

Expected System Behavior:

Payment status remains:

- Awaiting verification
- Disputed

The system:

- Does not mark payment as complete.
- Keeps all communication notes.
- Requires authorized review.

---

# Scenario 11: Database Service Outage

Situation:

Supabase temporarily becomes unavailable.

Expected System Behavior:

Mobile users:

- Continue limited offline operations.

Administrators:

- Receive system alerts.

The ERP:

- Prevents data corruption.
- Synchronizes safely after service recovery.

---

# Scenario 12: Malicious Record Deletion Attempt

Situation:

A user attempts to erase historical records.

Expected System Behavior:

The system:

- Prevents unauthorized deletion.
- Uses archive and reversal methods.
- Preserves audit history.

---

# Final Stress Test Principle

Every failure must answer:

- Can the farm continue operating?
- Can the data be recovered?
- Can the event be audited?
- Can the mistake be corrected?
- Can abuse be detected?

If the answer is no, the architecture must be improved.
